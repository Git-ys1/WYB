### 摘要

### 设计冻结（R2 优先规则）
1. 控制器优先顺序固定：
- `SSD1315_PAGE` -> `SSD1306_PAGE` -> `SH1106_PAGE_XOFF2(仅前两者失败后启用)`

2. 地址探测顺序固定：
- 先 `0x3C`
- 再 `0x3D`

3. 总线固定：
- 仅 `HW I2C2`
- 仅 100k（沿用 `MX_I2C2_Init()`）
- 不启 Soft-I2C / 不启总线恢复 / 不启重试状态机

4. 显示模式固定：
- 仅 `page mode`
- 命令/数据严格分离：
  - `oled_write_cmd()`：control byte `0x00`
  - `oled_write_data()`：control byte `0x40`
- 禁止 horizontal mode / dirty flush

### 实施步骤（决策完备）

#### Step 1：从 main.c 抽离 OLED 字节逻辑
- 删除 `main.c` 中现有 `SmokeOled_*` 实现（仅保留分流和故障灯函数）
- `main.c` 改为只调用 `bsp_oled_smoke` 的 API，不再直接 `HAL_I2C_Master_Transmit` 拼命令/数据包

#### Step 2：在 `bsp_oled_smoke.c` 实现统一底层发送规范
- 内部固定函数：
  - `static bool oled_write_cmd(uint8_t cmd)` -> `[0x00, cmd]`
  - `static bool oled_write_data(const uint8_t *buf, size_t n)` -> `[0x40] + n字节`
- 不允许命令数据混包发送

#### Step 3：实现 3 profile 的 init 与 page flush
1. `SSD1315_PAGE`（默认）
- init 序列按 SSD1306 兼容 page 路径，显式设置 page mode
- flush：每页 `B0+page`, `00`, `10`，再发 128 字节数据

2. `SSD1306_PAGE`
- 同 page mode 刷新策略
- 独立 profile 保留单独 init 序列，便于报告对比

3. `SH1106_PAGE_XOFF2`（保底）
- 132 RAM 列模型，显示窗口偏移 `x+2`
- 每页列起点设为 `2`（低列命令 `0x02`，高列命令 `0x10`）
- 仍只写 128 可见列

#### Step 4：测试流程固定（不可改顺序）
1. `Phase 1 命令链路`
- A5（500ms）-> A4（200ms）

2. `Phase 2 图案链路`
- 黑 -> 白 -> 竖条 `AA/55` -> 棋盘格（均 page flush）

3. `Phase 3 文本链路（仅在 Phase2 正常后）`
- 显示：
  - `OLED OK`
  - `PROF:1315/1306/1106`
  - `ADDR:3C/3D`
  - `CNT:xxxx`（500ms 递增刷新）

#### Step 5：PB12 故障灯编码更新
- `1` 闪：probe fail
- `2` 闪：init fail
- `3` 闪：pattern flush fail
- `4` 闪：三个 profile 全失败
- 正常运行：PB12 常灭

#### Step 6：main.c 分流逻辑（保持三路互斥）
- `APP_SMOKE_OLED_TEST==1`：只跑 OLED smoke（不进 app/bsp 业务）
- `APP_SMOKE_OLED_TEST==0 && APP_SMOKE_LED_TEST==1`：跑 LED smoke
- 双 `0`：回原业务入口（保持现有 superloop）

### 关键实现细节（避免二义性）
1. “profile 失败”定义分两层：
- 代码层失败：I2C NACK/timeout/init/flush 返回 false -> 自动切下一 profile
- 视觉层失败（花屏/偏移）无法由程序自动判定：通过 `PROF:` 显示让人工观察，必要时编译宏强制单 profile 验证

2. 加一个可选编译宏用于强制 profile（便于人工复核）：
```c
// -1: auto priority, 0:1315, 1:1306, 2:1106
#define OLED_SMOKE_FORCE_PROFILE (-1)
```

3. 首包记录：
- 在 `bsp_oled_smoke.c` 内记录第一包命令与第一包数据字节（静态缓冲）
- 供 `docs/oled_driver_report.md` 填写，不依赖串口

### 测试用例与场景
1. `T114L-PH1-01`
- 观察 A5/A4 是否生效（命令链路）

2. `T114L-PH2-02`
- 观察黑白/竖条/棋盘是否稳定（GDDRAM链路）

3. `T114L-PH3-03`
- 仅在 PH2 正常后进入文本计数显示

4. `T114L-PROF-04`
- 自动顺序验证 `1315 -> 1306 -> 1106`
- 记录每个 profile 现象：黑屏/花屏/偏移/正常

5. `T114L-ERRLED-05`
- 人为断线验证 1/2/3/4 闪故障码是否正确

6. `T114L-CONCLUDE-06`
- 若 OLED-only 正常：判定现有主工程集成污染
- 若 OLED-only 仍失败：判定底层显示链路问题

### 显式假设与默认
1. OLED 模组为 0.96" I2C，地址只考虑 `0x3C/0x3D`。  
2. 硬件连线维持 `PC4/PA8`，I2C 上拉到 3.3V。  
3. 本轮不使用任何恢复机制与软 I2C，以确保判定纯净。  
4. 文本阶段仅实现最小字符集，不引入复杂字库和排版。  
5. 本轮核心目的是“判定控制器与链路”，不是恢复原业务架构。
